## 1. C1 — 机制诊断错误，但结论方向对

### 报告说对的

- **不是加权采样，是确定性算法**。实测同一输入跑 100 次只产出 **1 种**排列（T0，`e1.distinct = 1`）。注释第 2424 行写「使用确定性伪随机」，代码里没有任何 PRNG——注释与实现不符，这一条报告说对了。
- **确实没有防霸屏机制**。算法只在窗口内按权重重排，没有任何「抑制同源相邻」的项。

### 报告说错的（两处，均有反例）

**（1）「完全等价于按 quality 降序排列」——证伪。**

3000 组随机权重实测，输出与 quality 降序一致的只有 **723 组（24.1%）**（T0，`e2`）。

反例（`e2.first_counterexample`）：权重 `[10,50,90,70,70,10]`，实测输出

```
x3(70), x2(90), x4(70), x1(50), x5(10), x0(10)
        ↑ 90 排在 70 后面
```

权重最高的 `x2` 被排到第 2 位。

**（2）「每轮都选中权重最大的元素」——证伪。**

`weights = {lo:10, w50a:50, w50b:50, hi:90}`（同窗口）实测输出：

```
[w50b, hi, w50a, lo]      ← 首轮选中权重 50 的 w50b，不是权重 90 的 hi
```

报告给出的等价性论据是 2 元素例子（S-HI 90 / S-LO 10）。**2 元素下任何非空确定性选取都输出同一顺序**，该例子不具备区分力（T0，`e4`）。

**最强反证（真实语料）**：前 200 位的平均 quality——

| 排序方式 | 前 200 位平均 quality |
|---|---|
| 纯 quality 降序（报告声称的等价物） | **99.26** |
| 纯时间降序（现状基线） | 82.20 |
| `diverse(120)` 实测 | **82.39** |

（T0，8788 条有日期条目，`analysis_snapshot.json` 的 1014 源质量表）

若 diverse 真等价于 quality 降序，首屏均值应逼近 99.26。实测 82.39，与时间降序只差 +0.19。

### 「完全未实现」不准确——真实效果（T0）

| 指标（前 200 位） | 时间降序 | diverse(120) |
|---|---|---|
| 榜首源 `agihunt_0` 占比 | 30/200（15%） | **22/200（11%）** |
| 同源最长连续 | 11 | **11**（无改善） |
| 平均 quality | 82.20 | 82.39（+0.19） |
| 位置发生变动 | — | 8754/8788（99.6%） |

准确表述：**机制有效性很低，但不是零**。榜首源占比降了 27%（相对），同源连续零改善。报告结论「打散目标未达成」**方向正确**，但「等价于降序」使它的**修复方向跑偏**（详见 §3.3）。

## 3. M1 — 不成立。窗口跨度上界就是 `windowMinutes`

报告称「一个窗口可以覆盖接近 2× windowMinutes 的实际时间跨度」。代码如下（`:2397-2408`）：

```javascript
var cur = [sorted[0]];
for (var i = 1; i < sorted.length; i++) {
  var tBase = new Date(cur[0].date).getTime();   // 锚点始终是组内第一篇
  ...
  if (... (tBase - tCur) <= windowMinutes * 60000) { cur.push(sorted[i]); }
```

`cur[0]` 在该组生命周期内**从不变化**，因此组内每一条都满足「与锚点间隔 ≤ windowMinutes」，组跨度**上界即 windowMinutes**。且 `sorted` 为降序，`tBase - tCur ≥ 0`，不存在负间隔把跨度拉长的路径。

实测（T0，`e5`）：

| 场景 | 最大组跨度 | 理论上界 |
|---|---|---|
| 稀疏（每 110 min 一篇 × 200） | 110.0 min | 120 |
| 随机（0–400 min 间隔 × 3000，2221 组） | **120.0 min** | 120 |

报告给的例子本身也不自洽：`10:00 → 组锚；11:50 入组；下一篇文章 08:00 → 差 120min → 新组`——`10:00 − 08:00 = 120 min ≤ 120`，应当**入组**而非新组；且例子中的时间在**递增**，与降序前提相反。

**M1 的真实形态**（值得记，但不是报告说的那个）：锚点不滑动，所以组内最新一条与最旧一条的关系是「≤ 120 min」，而**相邻两组之间可能有任意长的时间空隙**——这是「锚定分段」而非「滑动窗口」，属于设计选择，不是缺陷。

## 5. 报告漏掉的问题（含我自己的缺陷）

**（1）D16 是空断言——报告没发现。** `cases_diverse.js:198-214`：

```javascript
sortMode = '不存在的模式';
/* 回落由声明处的白名单完成；此处验证回落值 newest 仍产出合法时间序 */
sortMode = 'newest';          // ← 上一行赋的值从未被 applySort() 消费
applySort();
eq(..., 'new,old', 'D16 newest 时间降序');
ok(diverseOrder.length > 0, 'D16b ...');   // ← 恒真
```

第 208 行赋的非法值，在第 210 行**被直接覆盖**，中间没有任何 `applySort()` 调用。而且注释说「回落由声明处的白名单完成」——`:2325` 的 `sortMode` 声明**没有白名单**，非法值最终落到 `applySort()` 的最后一个 `else`（时间降序），恰好与 `newest` 同义，所以断言看起来过了。

变异验证（T0）：给非法值加一条错误分支 `else if(sortMode==='不存在的模式'){ ART.reverse(); }`，**D16 仍 GREEN**（Mut4）。D16b 断言 `diverseOrder.length > 0`，任何非空字符串都成立，恒真。

**（2）报告的 C1 修复建议内部矛盾。** 报告要求「引入 seeded PRNG 保证确定性」同时「将 D5 改为真正的统计分布断言」。但 seed 若由输入派生，**同一输入永远产出同一排列**，D5 的 100 次循环仍只得到 0/100 或 100/100 两种结果——统计分布断言在确定性种子的前提下不成立。要用分布检验就必须让 seed 逐次变化，那又破坏了它们自己要求的确定性。

**（3）报告的 C1 修复方向会把「时间可读性」推得更差。** 加权随机采样按 quality 加权抽取，其首屏质量均值会显著上移——实测纯 quality 降序的前 200 位均值已达 **99.26**（vs 时间序 82.20）。也就是说，把它改成「真随机 + 质量加权」，会让结果**更接近 quality 降序**，与这份方案自己的 Goal（「保持原有的时间维度可读性」）冲突。而且加权采样**仍不提供**同源不相邻的任何保证。

我的结论与上一轮一致：要达成「避免单源霸屏」，需要的是**同源窗口配额**（同源在窗口内超过 k 次则延后到下一个可用位），而不是给选取环节加随机性。

**（4）报告未覆盖的两个真实数据事实**：

- `quality = 0` 的源占 **496/1014 = 48.9%**，含 `google_deepmind`、`google_ai_blog`。`qm[sk] !== undefined ? qm[sk] : 50` 把 0 当作最低权重而非「未评分」，近一半源被系统性压到各窗口末尾（T0）。
- 仓库现存分块产物 tags 命中 0 次 → 功能尚未进入任何产物（T0）。
