## 一、战略定位问题

每日洞察与 RSS 洞察面板（`insight_engine.py`）定位重叠但质量更低，导致用户感知"每日洞察还不如 RSS 的洞察板块"。

| 维度 | RSS 洞察 (`insight_engine.py`) | 每日洞察 (`build_daily_insight.py`) |
|------|------|------|
| 数据源 | RSS feeds + Trending + 热榜（配额制） | RSS chunks + AIHOT + AGI Hunt + 热榜（四源） |
| 事件聚合 | 向量余弦相似度聚类（语义级） | Jaccard 标题字符串匹配（字符级） |
| 提示词 | 4 次独立 LLM 调用，每次有写法框架 + 正确示例 | 2 次 LLM 调用，裸提示词，零示例 |
| 深度解读 | narrative + causal_chains + outlook | Phase 2 深度解读（但全部失败） |
| 独有优势 | 无（数据源被每日洞察覆盖） | **跨平台共振**（40 热榜平台同时出现 = 破圈信号） |

**应有定位**：每日洞察应利用 RSS 洞察做不到的"跨平台共振"能力（40 个热榜平台 + AIHOT + AGI Hunt + RSS 四源共振），在内容维度上比 RSS 洞察**更深**（深度解读）和**更广**（四源共振）。

## 三、根因分析

### 根因 1: 实施遗漏（非设计遗漏）

原始设计对话（task-f82）中，用户明确要求"重版本"——包含完整写法模板、正确示例、Platform DNA 的提示词工程。这些设计进了 `insight_engine.py`（commit b900d51），但后来创建 `build_daily_insight.py` 时**未迁移**这些设计。

**证据**：
- `insight_engine.py` L1401-1470: 4 次独立 LLM 调用，每次都有 `## 写法要求` + `## 正确示例`
- `build_daily_insight.py` L1140-1144: 仅 4 行 system prompt，无写法要求、无示例

### 根因 2: 事件聚合方法降级

`insight_engine.py` 使用向量嵌入做语义聚类（通过 `_get_embeddings` + 余弦相似度），而 `build_daily_insight.py` 使用 Jaccard 字符串匹配。这是方法层面的降级，导致：
- 事件碎片化 → 同一话题被拆成多个事件
- 热榜平台分散 → heat 信号失效
- 跨源共振无法体现 → 丧失每日洞察的核心差异化能力

### 根因 3: 功能设计遗漏

原始设计对话中讨论了破茧栏（反信息茧房）和日报→周报→月报层级，但这两项功能在实施时被完全遗忘：
- **破茧栏**：设计为"与用户常读分组交集最小的 Top5 事件"，代码中无任何痕迹
- **周报/月报**：用户明确说"后期实现"，属于有意延期

### 根因 4: 质量闭环断裂

- Phase 2 深度解读全部失败 → `deep_analysis` 全为 null → 前端深度解读板块无内容
- RAGAS 评估解析失败 → 质量自审形同虚设
- 无自审-修正环节 → 单次 LLM 输出的错误无法被捕获和修正

## 四、BestBlogs 值得借鉴的设计模式

### 4.1 COSTAR 提示词框架

BestBlogs 的每个 LLM 调用都使用 COSTAR 结构：

| 维度 | 含义 | 我们的现状 |
|------|------|-----------|
| **C**ontext | 角色设定（"你是高级内容分析助手"） | 有但过薄（4 行） |
| **O**bjective | 具体目标（"快速分析文章并决定是否忽略"） | 隐含在 user prompt 中，未显式定义 |
| **S**tyle | 写作风格（"经验丰富的内容策展人"） | 无 |
| **T**one | 语气（"专业、客观、基于事实"） | 有但过简（"事实驱动"） |
| **A**udience | 受众（"网站内容管理团队"） | 无 |
| **R**esponse | 输出格式（JSON + 字段定义 + 示例） | 有格式定义但无示例 |

### 4.2 三阶段流水线

```
阶段 1: 初评过滤（LLM 四层判断 + 0-5 评分 + 8 个 few-shot 示例）
  ↓ ignore=true → 丢弃
阶段 2: 深度分析（LLM 四维度 90 分 + 减分机制 + 2 个完整示例）
  ↓
阶段 3: 检查与反思（LLM 6 维度审核 + 改进建议）
  ↓
阶段 4: 终优化（LLM 根据反思修正 + UpdateReason 追踪）
```

**对比**：我们的 `_verify_faithfulness` 是批量事实核查，不是逐事件自审+终优化。

### 4.3 结构化评分体系

BestBlogs 的深度分析评分：
- 基础分 90 = 内容深度(30) + 相关性(30) + 实用性(20) + 创新性(10)
- 减分项 -15 到 0（理论研究/营销导向/内容质量问题）

**对比**：我们的 `score` 是纯数学公式（`base_score × cross_mult × recency × accel_mult`），无 LLM 质量判断。

### 4.4 多源回退链 + 透明标记

BestBlogs 的回退链：`my_brief → for_you → following → public_brief → public_brief_fallback`，每步标记 `candidateSource` 和 `fallbackApplied`。

**对比**：我们的降级是静默的（如 Phase 2 失败后 `deep_analysis=null`，不标记原因）。

### 4.5 原语化 Skill 设计

BestBlogs 将能力拆成原子操作（`discover.today`, `read.deep`, `explain.article`），可组合链式调用。

**对比**：我们的 `main()` 是一个大函数，不可组合。

## 五、insight_engine.py 优秀提示词设计对比

### 5.1 写法框架

`insight_engine.py` 每次 LLM 调用都有明确的写法结构：

```python
# core_trends (L1405-1408)
"## 写法要求\n"
"1. 第一句话定性（使用'主导'/'分化'/'拐点'/'加速'等判断词）\n"
"2. 用【宏观主线】+【微观佐证】结构串联\n"
"3. 每个论点必须引用上下文中的具体事实\n"
"4. 禁止'综上所述'、'值得关注'等空话\n\n"

# rss_insights (L1429-1432)
"## 写法要求\n"
"1. 聚焦硬核增量：新技术路线、开源项目、论文、架构创新\n"
"2. 用【认知纠偏】+【硬核增量】结构\n"
"3. 必须指出专业视角如何修正大众热搜的误区\n"

# narrative (L1453-1456)
"## 写法要求\n"
"1. 必须呈现事件之间的因果/时间关系\n"
"2. 用'起因→发展→转折→结果'或类似叙事结构\n"
```

**对比**：`build_daily_insight.py` 的 Phase 1/2 提示词零写法框架。

## 六、当前产出质量快照

以 `daily-insight.json` 为例（最近一次构建）：

```
事件总数: 10
GPT-6 相关: 8 (80%) ← 话题被 AGI Hunt 绑架
deep_analysis=null: 10 (100%) ← Phase 2 全部失败
heat=0.0: 10 (100%) ← 热榜信号完全丢失
RAGAS overall: 解析失败 ← 质量闭环断裂
```

**结论**：当前每日洞察系统在事件聚合、提示词工程、质量闭环、前端呈现四个层面均存在严重问题，需要系统性修复。
