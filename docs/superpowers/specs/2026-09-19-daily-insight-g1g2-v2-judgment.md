## 我对这份分析的态度：同意其"真问题"清单，不同意其因果与优先级

四条主张（地基薄、检索自指、missed 被扔、修正不能增事件）经代码核实全部成立。**但作为工程决策，我有四点不同意见，每点都会改变实施方案：**

### 分歧 1：他高估了"二次检索"的必要性——missed 的补料 90% 已经在内存里
judge 只能看到 `context_text`（`_build_ragas_context` 从**已检索的 200 条 chunk** 构建，:4544）。所以 judge 报的 missed **必然是池内已有、但没进任何事件的素材**——真正的语料级缺口它对不上账，也就报不出来。结论：G1 第一步不该打检索，而是拿 missed 在 `retrieved_for_ragas` 里做语义匹配（FAISS 内存索引，零 API 成本）；池内找不到才回退定向召回。比他方案更便宜、更快、幻觉面更小。

### 分歧 2：cov≥0.75 有结构性天花板，他的方案绕不开
评估口径是"报告对 200-chunk 上下文的信息点覆盖率"。200 条 chunk 横跨几十个话题，而输出预算 MAX_EVENTS=12——**每补一个 missed 事件就挤掉一个既有槽位**，cov 提升是零和的。05:16 期 cov 0.75 是 9 事件拿到的，说明可达但吃运气。要真正稳定达标只有两条路：(a) 输出预算 12→16（页面变长，产品决策）；(b) 把 judge 的对照面从"原始 200 chunk"换成"蒸馏后的当日要点清单"（先让模型从池内提炼 top 信息点清单，再评覆盖——口径变了，分数才可比）。**这条必须让用户选，我不擅自改评估口径。**

### 分歧 3：他给"①喂正文→faith"的因果链不成立，真 faith 杠杆是 claim 层
我们 04:14/06:12 的 faith 事故复盘：幻觉发生在**证据存在时编数字、跨事件张冠李戴**（Diamandis→英王查尔斯），不是"素材不够所以编"。喂更多正文反而加大交叉污染面（素材 800→2500 字后，同 prompt 内可混淆的实体更多）。① 对 cov/内容质量有益，我照做；但 faith 的正解是他列的"claim/实体中间层"（先出主张-来源表再生成，引用可结构化校验）——他排最后，我认为那是 faith 唯一的架构级解，只是工程量大，本轮先以"证据包归属标注+终局核查"顶住，claim 层单独立项。

### 分歧 4：他的优先级建立在一个已坏的测量仪上——必须先要干净基线
过去一周所有 cov/rel/faith 样本都是在**文不对题 P0（下标配对错位）**污染下测的：judge 每期看到的报告本身标题正文错配，它的 missed/反馈都带着这个噪声。第7轮修复（eedd7cbc）02:00 构建才会上线。**地基改造的正确顺序是先拿 1-2 期干净基线，再动 G1**——否则 G1 上线后分数变化无法归因（是补事件起效，还是错位修复起效？）。这不是保守，是测量学要求。

### 他完全没提、但影响设计的两点
- ③（多路查询扩面）对指标不可见：judge 只看池内 200 条，语料召回扩面改善的是**产品真实价值**（读者看不到的好内容），不会动 cov 分数。做，但不能拿分数向自己证明它有效，需以"新增事件来源分布"单独观测。
- build_rss_aggregator 全文抓取正被另一会话在途修改（rss_fetch_state 重构），① 中"扩全文覆盖率"的部分本轮不碰，只做已命中正文的利用方式升级。

## 实施（TDD→fresh-eyes 对抗审查→pathspec 提交→Data API 推送）

### G0（前置，零代码）：第7轮干净基线
02:00 构建（head eedd7cbc）后核验：标题/正文一致性（人工抽 3 事件）、事件数 10-12、med= 中位日志、语义近邻日志。连续 1-2 期后 G1 开工。

### G1 missed 闭环（改 self-contained，主杠杆）
1. `_evaluate_report_quality` 解析回收 `reasoning.coverage.missed`（v1 :3020）/`missed_points`（v2 :3054）→ 返回 dict 加 `missed_points`，`_median_eval_samples` 并集透传。
2. 新函数 `_recover_missed_events(missed, retrieved_for_ragas, clusters)`：missed 短语 → 对池内 chunk 做 `_cos_sim`/`_dedup_tokens` 混合匹配（阈值：cos≥池内中位数 或 token overlap≥3）→ 命中 chunk 按 URL/标题聚 1-2 组 → 与既有事件 jaccard 查重（防重提已覆盖）→ 产出新 cluster（items 带来源）。
3. 新事件走 `_llm_phase1`（单批复用现有 event_num 配对与 `_validate_key_links`）→ append → 现有终局闸序（dedup/占位/faith recheck/cap :4666-4690）天然覆盖，链接红线由校验保证。
4. 预算：`len(clusters) < MAX_EVENTS` 才补，每构建 ≤2 事件；池内无着落的 missed 才做 `_hybrid_retrieve` 定向补查（top_k=30，missed 短语数≤5）。
5. 测试：missed 解析（两格式）；池内匹配命中/挡幻觉；与既有事件重叠不重提；新事件过全闸；embed/检索失败静默降级；MAX 不越界。

### G2 证据利用升级（Phase2 三事件专用）
- `_build_event_material` 与 `_build_evidence_pack` 合并去重：URL 命中 full_content 的 item 直接用正文（段落边界截 2500），证据块跳过同 URL；未命中行为不变。
- 注入前近似转述去重：`_dedup_tokens` jaccard>0.7 的 item 只留 heat 最高一条。
- 测试：命中时素材含正文且无重复注入；近似 3 留 1；回退路径不变。
