# 夜间独立深度洞察管线 · 修正版设计规格（漏斗补全）

- 日期：2026-09-23　状态：待批准
- 本文与 `2026-09-22-nightly-deep-insight-design.md` 的关系：**不推翻它的隔离/并发/发布政策/产物治理**（那四块已在现网验证过，照旧生效）；本文**补它缺的四个阶段，并作废其中三条被证据推翻的条款**（见 §2）。
- 决策链照旧：每一节都注明"被哪一轮读数逼出来"。没有读数支撑的句子一律标"待验假设"，不许当依据用。

## 1. 为什么要出这一版（一句到根）

初版把力气全花在**"一条怎么写得长、写得像深度"**上（§2 四条判据 + 两段式生成 + 4,000–10,000 字换档），
但**"哪些锚点值得写、写完的信不信得过、判分稳不稳"这三段漏斗根本没建**。
白天管线这三段都有，而且是十几轮故障逼出来的（`build_daily_insight.py` 里带行号可查）。

用户 2026-09-23 的判断原话：**"我们在旧构建里面设计的洞察管线在新的深度洞察管线里面没有了，没有了筛选，没有了评判，没有了质量打分。"**
逐条对代码核实后成立。实测后果见 §3。

## 5. 修正后的管线（八段漏斗，每段注明"哪一轮故障逼出来的"）

```
S0 锚点归并  → S1 值得写快筛 → S2 证据装配(派生自长度契约) → S3 提纲(主证据互斥)
   → S4 逐段成文 → S5 结构补齐+契约 → S6 逐条事实核查 → S7 判定(多遍中位+采纳闸)
   → S8 收口发布
```

### S0 锚点归并（新，P0）
- 做什么：对 `daily-insight.json` 的锚点两两判同题，**机械提名 + agent 定夺**：先用标题/摘要词面重叠率提名候选对，再让 agent 回答"是不是同一件事、能不能并"，并必须给出理由。
- 为什么不是纯阈值：白天 9/17 那次"同 label 不同内容"错并就是纯阈值干的（`_semantic_dup_round:2449` 的注释写明它要 summary 独立成签名才敢并）。夜间沿用同一教训：**阈值只提名，语义判定交 agent**。
- 合并动作：`links` 取并集、`title` 取信息量最高者、被并掉的 id 进 `merged_from`；审计写 `anchor_diff` 的 `op:"merge"`，`evidence_before/after` 用**合并后实际可用素材字数**（不是条数）——本场 evt_011 那个字段写的是 3→5，读的人分不清是什么从 3 变 5。
- 失败动作：agent 不给结论 → **不并**（宁可留副本也不能错并），并记 `merge_skipped: [{pair, reason}]`。
- 判据：同题三副本喂进去必须并成 1；"同标签不同内容"的反证对不许并；agent 缺席时保持原样。

### S1 值得写快筛（新，P1）
- 做什么：合并后每条锚点算一份**素材与新颖度的机械画像**（独立源数、长文数、总字数、跨天是否已写过、`quality.tier` 分布），交给 agent 判"配不配一条 4,000–10,000 字"，产出 `deep_worthy: true/false` + 理由。
- 为什么：初版把"值不值得写"完全交给证据门，结果 evt_005（篇均 897 字）走完整条生成链才死在门上。
- 关键约束：**不学白天的 55 分门槛当硬门**。`MIN_DEEP_SCORE=55` 在白天是**名额分配器**（`DEEP_ANALYSIS_TOP_N=3`），夜间没有名额稀缺问题（一夜 12 条）；夜间用它当否决，就是在拿别人的预算约束当质量标准。所以 S1 只产出"候选 + 理由"，被拒的锚点直接按快讯呈现并写明拒因，**不进入生成、不烧调用**。
- 跨天查重：`predictions.jsonl` 已经有"读现网→整库写回"的成熟套路，这里加一份 `covered.jsonl`（date, anchor_key, title），**已深挖过的锚点次日不许再深挖**，除非合并后的新素材字数超过旧记录 1.5 倍。理由：本场三条锚点全在同一条新闻上，而这条新闻昨天已经写过。

### S2 证据装配（改，P1）
- 现有 `evidence_gate` 的三条硬码（`GATE_MIN_SOURCES=3 / GATE_MIN_TOTAL_CHARS=12000 / GATE_LONG_CHARS=3000, MIN_LONG=2`）里，**12,000 这条与长度契约脱钩**：它是按旧 2,500–4,000 字契约定的，现在一条要写 4,000–10,000，门槛应当随**要写的长度**派生，而不是停在旧值。
- 改成：`required_material_chars(n) = n * MATERIAL_RATIO`，`MATERIAL_RATIO` 现测先定（本场 evt_005 篇均 897 字、evt_008 素材/成文比 ≈13×、evt_011 ≈64×）→ **首版取 8×并按下限 4,000 字算 = 32,000 字素材**；上线后用三场真实分布复核。
- 同时新增一条装配侧要求：`select_articles` 必须**保证选出的篇章数 ≥ `required_sources(NARR_MAX)`**，否则当场降级并记原因，不要等生成完 30 次调用后再由 `validate_event` 判死。
- 判据：素材不足的锚点**一次调用都不许发**（这条现在做不到，evt_005 是发了调用才发现）。

### S3 提纲（改，P1）
- 现在只要求 `sections[].evidence` 从合法编号里选，**没有要求各段主证据互不相同** → 8 段抢同一批富源是结构必然。
- 加：每段必须给 `primary`（一个编号），且 **`primary` 在段间不得重复**；段数上限同时受可用源数约束 `outline_section_cap(n_sources)`。
- 提纲被拒的真实退路：`staged_generate` 现在已有"提纲给的段数 < PARAS_MIN → 退回单趟"，`primary` 冲突走同一条路（返回 `None + note`），**不许只打日志然后照常开写**。

### S4 逐段成文（保留）
两段式、每段只带本段证据、短段本趟补一次、组装按整段丢不截半句 —— 初版 §10.12 的这套不动。

### S5 结构补齐 + 契约（改，P0）
1. **覆盖解钳**：删掉 `min(len(cited_ids), …)`，改为 `required_sources(n) = ceil(n / EVID_CHARS)`，并同时要求 `len(citations) ≥ required_sources(n)` 与 `used_cov ≥ required_sources(n)`。派生值单一来源（`_structure_rules` 与 `validate_event` 共用一个函数，不许两处各算）。
2. **`quality.verdict` 复合值归一**：`repair_quality_verdict()` —— 按 `/`、`、`、`,` 拆，各部分都落在枚举内则取第一个并记 `verdict_repaired`（留痕，不许静默改判）；拆不出合法值仍判不合格。这是 S6 那类"按格摘除"政策在枚举字段上的延伸，直接省下 evt_008 那种整条烧掉。
3. 已有 `repair_forecasts()`（§10.16）照旧。

### S6 逐条事实核查（新，P0）
- 做什么：正文与 claims 定稿后，把**每条 claim 连同它引用的那几篇证据**单独送审（一次一条，带证据原文，不带别的 claim），判"这句在给定证据里有没有支撑"，输出 `supported / unsupported / inflated(数字对不上)`。
- 失败动作：`unsupported/inflated` 的 **claim 摘掉并记 `claims_dropped`（含原文与判定理由）**，不废整条 —— 与 §10.16 的"一格违约只摘那一条"同政策。摘到 claims 少于 `CLAIM_MIN` 才整条降级。
- 为什么必须有：现网正文里那句"2026 年第三季度企业 AI 服务采购数据显示，OpenAI 占约 58%、Anthropic 约 22%"在我方 5 篇引源里找不到出处。而 `validate_event` 查的是"编号存在"，查不出"编号存在但这句话不在里面"。白天为此写了 `_verify_faithfulness`，两轮才修对（`global_context_chunks` 那段注释就是"judge 看得见、核查编辑看不见"的教训）。
- 硬约束：核查方看到的证据**必须是该 claim 引用的那几篇全文**，不是摘要、不是截断片段（`_ragas_ctx[:12000]` 那类按字符切的写法在白天已被证明错，见白天 `:118` 注释）。
- 成本口径：核查调用数 = claims 数（3–10）× 合格条目数。这条与 S7 一起决定 §7 的预算重算。

### S7 判定去噪（改，P1）
- `judge_event` 从单遍改成 **2 遍取中位**（`JUDGE_SAMPLES=2`；三遍的收益要先看 §6.3 的实测方差再定，不许先加）。
- **停滞边界（原写"采纳闸 + 回滚原版 + `regen_rejected`"，落地时改判，见 §10 批 3.5 与台账 §10.17）**：
  夜场没有可比的"改前基线"——白天那套是同一份文本 v1→v2→v1' 的复评配对，我们比的是**两个被改写过的版本**
  的独立中位均值。照抄"没超边界就不许改"会把 0.6375→0.90 这种真改进也冻掉。
  所以 `beat_by_margin`（阈值 0.09 = 复评极差 0.17 的一半）只用来回答**"还要不要再重写一轮"**：
  连续两版没好出边界且不在近线豁免带内 ⇒ 提前收手并记 `regen_stalled`。一版合格就采纳，不存在回滚，
  `regen_rejected` 这个字段在夜场不存在。
- **压线不给记功**（A6 的落地形态）：两样本极差超过边界 ⇒ 不当最终答案，留作兜底再重判一轮；
  三轮都抖才采纳，并打 `judge_borderline`，页面标注极差、`budget.borderline` 计数。
- 把 §6.2 的机械读数（`restate_rate`、被 ≥3 段复用的数值清单）注入 judge prompt，作为 density 维的**输入证据**而不是阈值。agent 主判、机械提名 —— 用户 9 月点名的这条纪律在这里同样成立。
- 观测：产物里记 `judge_samples: [mean1, mean2]` 与 `judge_spread`，让"这条是稳过的还是抖过的"可读。

### S8 收口与发布（保留，含 §10.16 改判）
`can_publish` 只拦半套；全降级照发布 + 页面横幅；站内链接红线不变。

## 6. 产物 schema 变更

1. `anchor_diff[].op` 取值补 `merge`，并新增 `merged_from: [id…]`；`evidence_before/after` 明确为**素材字数**（字段改名 `material_chars_before/after`，避免"3→5"这种无法解释的读数）。
   **实现偏差（2026-09-24 记）**：改名**没做**，代码里仍是 `evidence_before/after`
   （`build_deep_insight.py:2835/2838/2844/2849`）。改名会连动 anchor_diff 的页面渲染与探针，
   不属于本批范围；语义按本条读（是素材字数，不是条数）。要改的话单开一批带读者同改。
2. `repeat_rate` **退役**，换 `restate_rate`（0–1，段落级数值复用）+ `restate_pairs`（int）+ `restate_top`（被几段复用的数值清单，最多 8 个）。`clip_for_degrade` 与降级早退路径两处都要写（这条不变量已有判据守着，改字段名时必须一起搬）。
3. 条目新增：`claims_dropped:[{claim, verdict, reason}]`、`faith_checked:bool`（**实作为 `faith_summary.checked`**，同一件事换了落点：核查数/留下数/摘除数/低于下限旗标一起记，见 `apply_faith`）、`verdict_repaired`（可缺）、`judge_samples`、`judge_spread`、`deep_worthy_reason`。
4. 顶层新增 `covered_ref: {anchors_today, already_deep_before}`，用于证明"跨天不重复深挖"这条真的在跑。

## 7. 预算重算（先量后定，不许先写死）

现网实测：3 锚点 / 50 次调用 / 634.6s / 输入 1,647,379 token（`workers=3`，4 把 key）。
新增调用面：S0 合并判定（候选对数，估 ≤ 锚点数）、S1 每锚点 1 次、S6 每合格条目 ~8 次、S7 judge ×2。

- **批 3.8 实测更正**：`PER_ATTEMPT_CALLS` 只是**标称值** 31（提纲 2 + 逐段 2*SECTIONS_MAX + 结构 1 + 双判 2 + 核查 10）。
  段数是模型给的、我们按 §12.3 不硬截断，所以真成本随段数走：12 段提纲一趟实测 **37** 次。
  `CALL_CAP` 仍是 684（**故意不抬**），`ITEM_CALLS_MAX=93` 只是"一条最坏要花多少"的标称上界，闸改成正经的**每趟问一次**。
- 新公式须含：`outline + sections(2*SECTIONS_MAX) + structure + faith(CLAIM_MAX) + judge*JUDGE_SAMPLES` ⇒ 最坏 `1+16+1+10+4 = 32`/趟，`12*3*32 = 1152`。

## 12. 落地后的两处改判（2026-09-24 凌晨，按现网证据与本会话纠正）

**① §5 里"提交通道独立"这个说法作废，改成"提交必须让位"也一并作废。**
本文 §5 原打算给夜场加一道"写主干前查有无在途构建，有则让位"的守门。用户当场否掉：
「仍旧要执行 白天跑时必须照样提交成功，这是独立的」。这条纠正成立 ——
白天场 `Update Star Hub` 每小时一场，让位＝夜场永远发不出去，与 §10.16 已定的
「停更比快讯更糟」是同一个错误方向。
最终规则：**夜场提交不查任何人在不在跑，撞车由 CAS 重试用尽后的 `reverted/failed` 记账吸收**；
并且新加一条判据，`publish` 通道源码里出现 `actions/runs` / `in_progress` / `gate()` 任一形态即红，
防止以后有人（包括下一次的我）把让位闸以另一种形状加回来。

**② 覆盖判据的派生要求必须被"我们供给了几篇来源"封顶，而不是被"模型自愿引了几篇"封顶。**
本文 §5 S5 写的 `required_sources(n) = ceil(n/EVID_CHARS)` 直接落地时会造出一条**满足不了的要求**：
测试夹具池子只有 6 篇源，9,933 字的条目无论如何引不出 7 篇 —— 那判的是我们，不是它。
现在 `need_cov = min(required_sources(n), supply)`，`supply = len(valid_ids)`；
供给少于派生要求时记 `sources_short=(字数, 需要, 供给)` 进条目，作为批 4（证据门按长度派生）的定档依据。
这与刚拆掉的老钳制不是一回事：老的按"它自愿引了几篇"收敛（可以少引再少要求），
新的按"我们给到几篇"收敛（我们的责任边界），并且两头都有判据（引满 6 篇必须放行、只引 3 篇必须判死）。

**③ §5 S3 的"段数受源数约束"不许做成硬截断。**
硬砍段数会把总长度削回上限以内，于是"组装守上限"那道守卫自己失效
（变异体 N11 现场演示：8 段被砍成 6 段后 `trimmed_sections` 恒为 0）。
上限只进 prompt 约束模型，代码侧超了只记 `sections_over_sources` 不砍；
主证据撞车的处理是**点名重问一次提纲**，仍撞车则带账继续写（`primary_collisions`），
而不是整条退回单趟 —— 退回单趟等于把压住长度方差的那一步废掉。
