# StarHub RSS 聚合器：信源丢失修复 + 时效性提升方案

> 日期：2026-09-16
> 状态：方案确认

---

## 一、问题诊断

### 1.1 现象

配置 1000+ 个 RSS 信源，前端仅展示 500+ 个有内容的信源，约 400+ 信源始终为空。

### 1.2 根因链（已修复）

```
域名级熔断（Semaphore 2 + 连续 3 次失败封禁整域）
    ↓ 大量源首次抓取失败
历史为空（rss_history.json 无该源记录）
    ↓
增量模式跳过陷阱（Fix 1 修复前：历史为空仍被跳过 → 永远无法恢复）
    ↓
_accumulate_history 数据替换效应（Fix 2 修复前：刚抓取的数据被空壳替换 → 依赖 72h 历史回填）
    ↓
构建日志口径不一致（Fix 3 修复前：ok_count 报抓取阶段数字，total_items 被历史重组覆写）
```

### 1.3 额外发现：设计缺陷

72 小时统一窗口对低频优质源过于激进——更新频率低于 72h 的源（如周刊、月刊）内容永远被裁剪。

---

## 二、已实施的修复（Fix 1-4）

### Fix 1: 增量跳过陷阱修复

**文件**: `build_rss_aggregator.py` 增量分流逻辑

**改动**: 当历史为空时，即使 `last_fetch` 在阈值内，也强制重新抓取。

```python
if (now - prev_time).total_seconds() < threshold:
    # 历史为空时不跳过，强制重新抓取以恢复数据
    if not _hist_by_key.get(key):
        _to_fetch.append((_i, src))
        continue
    skipped_count += 1
```

### Fix 2: _accumulate_history 保留抓取结果

**文件**: `build_rss_aggregator.py` `_accumulate_history` 函数

**改动**:
- 先用当次抓取结果初始化 `src_map`（不再用空壳替换）
- 历史数据仅作为补充，按 `link` 去重后合并
- 保留原始 items 顺序，历史数据追加在末尾

### Fix 3: 构建日志口径统一

**文件**: `build_rss_aggregator.py` 构建主流程

**改动**: `_accumulate_history` 返回后重新统计 `ok_count`，确保日志反映最终产物状态。

### Fix 4: T4 长尾层

**文件**: `build_rss_aggregator.py` 多处

- **4a 常量**: 新增 `_TIER_HISTORY_HOURS = {1:72, 2:72, 3:72, 4:168}`（T4 = 7 天）
- **4b 自动晋升**: 连续 3 次构建所有文章 pub_date > 72h → 晋升 T4，持久化到 `source_tier_promotion.json`
- **4c tier 级 cutoff**: `_accumulate_history` 内按 tier 使用不同裁剪窗口
- **4d 发现页推荐**: 前端 `_discoverKeys()` 优先纳入 T4 源，增加长尾徽章

### 修复效果验证

对抗性审查 28/28 项全部通过（红队攻击 5 组 + 变异测试 3 项 + 真实数据量验证 6 项）。

## 三、时效性问题分析

### 3.1 当前数据延迟

构建时间表（GitHub Actions cron）：

| UTC | 北京时间 | 模式 |
|-----|---------|------|
| 21:00 | 05:00 | 全量 |
| 02:00 | 10:00 | 增量 |
| 06:00 | 14:00 | 增量 |
| 10:00 | 18:00 | 增量 |
| 14:00 | 22:00 | 增量 |

- **平均延迟**: 4-5 小时
- **最坏延迟**: 7 小时（22:01 发布 → 次日 05:00 构建）

### 3.2 增加构建频率不可行

| 约束 | 实际数据 | 影响 |
|------|---------|------|
| **GitHub Actions 月时长** | 免费 2,000 分钟/月；当前 ~5 次/天 × ~15 分钟 ≈ 2,250 分钟/月 | **已超额** |
| **单次构建耗时** | 全量 8-21 分钟；增量（900+ 源）5-**45 分钟** | 重叠风险高 |
| **cancel-in-progress** | 新构建取消正在运行的构建 | 数据不完整 |
| **Vercel 部署** | 每次 `vercel --prod` 额外 1-2 分钟 | 叠加耗时 |

### 3.3 结论

构建频率无法提升。时效性问题需通过**前端实时刷新**解决。

## 四、架构决策：快照 vs 实时

### 4.1 为什么保留快照机制

| 考量 | 分析 |
|------|------|
| 国内可达性 | 用户个人使用 + VPN，Vercel 可达 → **不再是需要** |
| 首屏加载速度 | 快照秒级加载 vs 实时抓取需等待网络 IO → **快照仍有价值** |
| Vercel 配额 | Hobby 1,000 次/天 Serverless 调用，个人使用充足 |
| 单次超时 | Vercel Hobby 10 秒限制，1000 源并发抓取 >> 10s → **全量实时不可行** |

### 4.2 最终架构：快照为主 + 实时增强

```
┌─────────────────────────────────────────────────────┐
│                    前端页面                           │
│                                                     │
│  ① 加载快照数据（秒级首屏）                           │
│  ② 用户点 refresh → 调 /api/rss?refresh=1           │
│  ③ 实时数据覆盖快照数据（浏览器内存级）                 │
└──────────────┬──────────────────────────────────────┘
               │
    ┌──────────┴──────────┐
    │                     │
    ▼                     ▼
┌─────────┐        ┌──────────────┐
│ 快照层   │        │  api/rss.js  │
│(构建产物)│        │ (Serverless) │
└─────────┘        └──────────────┘
    ▲                     │
    │                     ├── 有快照 → 先返回快照（秒级）
    │                     │   └── 同时后台更新缓存
    │                     │
    │                     ├── refresh=1 → 实时抓取
    │                     │   ├── T1: 8 个源，实时翻译（已有）
    │                     │   └── T2/T3: 按需分批抓取，不翻译
    │                     │
    │                     └── 无快照 → 实时抓取兜底
    │
    │
┌───┴──────────────────────────────────┐
│         GitHub Actions 构建           │
│                                      │
│  全量/增量抓取 1000+ 源               │
│  → 翻译英文内容                       │
│  → 写入 rss_api_snapshot.json        │
│  → 写入 rss_history.json             │
│  → vercel --prod 部署                │
└──────────────────────────────────────┘
```

### 4.3 两条管线互不干扰

| 维度 | 构建管线（GitHub Actions） | 实时管线（api/rss.js） |
|------|--------------------------|----------------------|
| 触发 | cron 定时 | 用户手动 refresh |
| 数据持久化 | 快照 + 历史文件（持久） | 浏览器会话（临时） |
| 翻译 | 全量翻译（Python 管线） | 仅 T1 翻译（不翻译 T2/T3） |
| 对下次构建的影响 | 写入 last_fetch / history | **无影响**（不持久化） |
| 去重 | 基于 link 的历史去重 | 前端基于 link 去重 |

## 五、实时刷新增强方案

### 5.1 当前状态

`api/rss.js` 已支持：
- T1 源（8 个）实时抓取 + 翻译
- T2/T3 源从快照读取
- `refresh=1` 参数触发 T1 实时抓取

### 5.2 增强目标

用户点击 refresh 时，**T2/T3 源也能获取最新数据**。

### 5.3 实现方案

#### 5.3.1 分批懒加载（解决 10s 超时）

```javascript
// api/rss.js 新增逻辑
if (refresh === '1' || refresh === 'all') {
    // 分批抓取 T2/T3，每批 50 源，避免超时
    const batchSize = 50;
    const t2t3 = sources.filter(s => s.tier >= 2);
    
    // 方案 A: 前端分批请求
    // GET /api/rss?refresh=1&batch=0    → 源 0-49
    // GET /api/rss?refresh=1&batch=1    → 源 50-99
    // ...
    
    // 方案 B: 后端异步，先返回快照，后台更新
    // 首次请求 → 返回快照 + 标记 stale
    // 前端轮询 /api/rss?meta=1 → 检查更新完成
    // 完成后返回新鲜数据
}
```

**推荐方案 B**（后端异步）：
- 用户体验更好（先看到快照数据，后台静默更新）
- 不受 10s 超时限制（后台异步完成）
- 但需要 Vercel 支持后台运行（Serverless 函数返回后不再执行）

**实际可行方案 A**（前端分批）：
- 每批 50 源，~5s 内完成（符合 10s 限制）
- 前端逐批请求，合并渲染
- 20 批 × 5s = 100s 完成全部刷新（可接受，且可中断）

#### 5.3.2 翻译策略

| 场景 | 策略 | 理由 |
|------|------|------|
| T1 英文源 | 服务端实时翻译（已有） | 8 个源，量小 |
| T2/T3 英文源（实时刷新） | **不翻译，显示原文** | 用户能读英文；翻译会超时 |
| T2/T3 英文源（下次构建后） | 构建管线翻译 | 构建无 10s 限制 |
| 浏览器端翻译（可选增强） | 前端调 translate.js 的 bulk 模式 | 不消耗 Vercel 时间 |

#### 5.3.3 前端交互

```
页面加载 → 显示快照数据（秒级）
         → 顶部显示 "数据更新于 X 分钟前"
         
用户点 refresh → 显示加载动画
              → 分批请求 T2/T3 实时数据
              → 逐批合并渲染
              → 完成后更新 "数据更新于 刚刚"
              → 英文源显示原文 + 可选 "翻译" 按钮
```

### 5.4 翻译负载分析

| 模式 | 翻译量 | 耗时 | 可行性 |
|------|--------|------|--------|
| 构建时全量翻译 | ~1,700 条新翻译 | ~30 分钟（Python 管线） | ✓ 已有 |
| T1 实时翻译 | ~50 条 | ~3 秒 | ✓ 已有 |
| T2/T3 实时翻译 | ~1,700 条 | ~30 分钟 | ✗ 超时 |
| T2/T3 不翻译 | 0 | 0 | ✓ 推荐 |

## 七、风险评估

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| 分批刷新时 Vercel 限流 | 低 | 每批间隔 500ms，单日个人使用远低于限额 |
| 实时数据与快照数据不一致 | 低 | 前端基于 link 去重，以最新数据为准 |
| 英文源实时刷新无翻译 | 低 | 用户能读英文；下次构建自动翻译 |
| 上游 RSS 服务封禁 Vercel IP | 中 | 分批 + 限并发；域名熔断已有保护 |
| GitHub Actions 月时长超额 | **已发生** | 不增加构建频率；依赖实时刷新替代 |

## 八、不变量约束

以下约束在方案实施前后均必须保持：

1. **构建产物完整性**: 快照必须包含所有 1000+ 源的数据（无论是否有文章）
2. **历史去重**: 同一 link 不重复出现在同一源的历史中
3. **T1 实时性**: T1 源始终由 api/rss.js 实时抓取，不参与构建阶段
4. **翻译缓存**: translations.json 作为翻译缓存，避免重复翻译
5. **增量安全**: 历史为空的源在增量模式下必须被重新抓取（Fix 1）
6. **日志一致**: 构建日志的 ok_count 和 total_items 必须反映最终产物状态（Fix 3）
