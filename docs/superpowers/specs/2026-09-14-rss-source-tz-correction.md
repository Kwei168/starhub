# Spec：源级时区误标校正 + 未来日期处置（2026-09-14）

## 1. 现象

首屏前 7 位中 6 位是**同一个源**（超能网），且这 6 张卡片的时间标签都是「刚刚」——
它们的时刻完全相同。这与上一轮修掉的「无日期条目置顶」是**不同**的缺陷：
这批条目有 `pub_date`，而且是个错误的值。

## 2. 证据（全部实测，非推断）

### 2.1 超能网 `pub_date` 系统性晚 8 小时

`rss_history.json` 中 `超能网_31` 共 37 条，36 条命中「日期倒挂」（`pub_date > first_seen`）：

| 指标 | 值 |
|---|---|
| 配对观测 n | 37 |
| 倒挂率 | 97.3%（36/37，阈值 `<-10min`）|
| `first_seen - pub_date` 中位 | **-6.25h** |
| 区间 | [-7.41h, +3.11h]，stdev 1.67h |
| 按 **-8h** 校正后 | 残留延迟 [+0.59h, +11.11h]，**全部为正**，中位 +1.75h |

抓取延迟必须 ≥ 0（我们不可能在文章发布**之前**抓到它）。所以校正后残留必须全为正——
这条物理约束把偏移量唯一确定在 **8 小时**，与「北京时间被标成 `+00:00`」完全一致。
观测到的「约 6 小时」= 8h 误标 − 1.75h 抓取延迟。

### 2.2 放大机制在前端钳制

`buildArt()` 的时区安全钳制（`:2071`）把**每一条**未来日期改写成 `now`：

```js
if(!isNaN(_t)&&_t>nowMs) a.date=new Date(nowMs).toISOString();
```

N 条未来条目因此获得**完全相同**的时刻 → 默认 `newest` 降序排序下同刻并列 →
稳定排序按插入序整块占据首屏顶部。这是「6 条同刻挤在顶部」的直接成因。

### 2.3 审计只标记不校正

`bad_date` 审计（`:402-425`）算出 `_unreliable_srcs` 后，只写一个布尔标记；
`pub_date` 原样进入输出条目 `d`（`:463`）。所以错误日期一路走到前端。
副作用：超能网被计入 `_LAST_UNRELIABLE_SRCS`，其关键词在趋势/关键词提取里被 0.3 倍降权——
一个**时区解析问题**被误判成**内容质量问题**。

### 2.4 影响面（决定实现形态）

| 分类 | 条数 | 处置 |
|---|---|---|
| 未来日期条目（全量） | 365 / 108 源 | — |
| 其中**所属源仍在 `rss_sources.json`**（真的会渲染） | **146** | 本 spec 覆盖 |
| 其中已移除来源（不渲染） | 219 / 96 源 | 不处理 |
| 「紧致整点带」时区误标（超能网 36、product_hunt 24） | 60 | 源级校正 |
| 「宽阔带」预约发布（arxiv 31 等） | 86 | 降级键 |

判别依据：超能网区间 [3.94h, 7.40h] 紧致 → 单一固定偏移；
arxiv_ai_4 区间 [-23.86h, +17.23h] 且倒挂率仅 51.7% → 不是时区问题。

### 2.5 第二实现的存在（约束实现位置）

`api/rss.js` 是**独立**的服务端实现。`refresh=1` 时它对 tier-1 源
自己用正则重解析 feed（`:216-275`），且：

```js
pub_date: pubDate || new Date().toISOString(),   // 无日期 → 伪造成「现在」
```

它**没有** tz 校正、没有 `bad_date` 审计、没有降级标记，且 `filterItems`
对无日期条目直接 `return true`（绕过 72h 窗口）。

→ 结论：校正不能只写在 HTML 内联 JS 里，必须落在**数据层**（构建期写入输出条目），
两个通道读同一份数据才不会互相打脸。

tier 分布核对：`超能网_31` = tier 2、`product_hunt_797` = tier 3 → 走快照通道，构建期校正即可覆盖；
未来日期源中仅 `arxiv_ai_4` 是 tier 1（它属「宽阔带」，走降级键路径）。

## 3. 设计

三层，按「证据强度」递减：

### L1 源级时区误标校正（根因层，自动检测）

判据：**我们不能在文章发布前抓到它**。故 `first_seen - pub_date` 系统性为负
⇒ `pub_date` 已证伪 ⇒ 存在固定偏移。校正量 = 让全部观测回到物理可行域所需的**最小**合法 UTC 偏移。

守卫（全部满足才校正）：

| 守卫 | 值 | 理由 |
|---|---|---|
| 配对观测 n | ≥ 8 | 小样本统计不可信 |
| 倒挂率 | ≥ 90% | arxiv 51.7%、product_hunt 80% 被排除 |
| 候选偏移 | ∈ IANA 合法集（整点 -12..+14，另加 5:30/5:45/6:30/8:45/9:30/10:30/12:45/-3:30/-9:30） | 只可能是真实时区 |
| 校正后最小延迟 | ≥ -10min | 物理约束，容忍时钟漂移 |
| 校正后中位延迟 | ∈ [0, 24h] | 抓取延迟合理性 |

实测命中：`超能网_31` → **-480min**。其余 1013 个源均不命中。

### L2 残留未来日期 → 降级键（通用层，必须保序回拉）

L1 之后仍 `pub_date > first_seen + 1h` 的条目：该日期同样已被证伪
（我们不可能在发布前抓到），改用 `first_seen` 作排序键，**复用现有 `date_fallback` 机制**
（前端显示「收录 X」，与发布时间区分）。

- 阈值 1h：容忍两端时钟漂移；超过即不可信。
- 为什么不是「钳到 now」：钳到 now 制造同刻并列（现象本身）；沉底让条目不可见（用户已否决）。
  降级键是一个**我方记录的、可参与排序的真实时刻**，语义诚实。
- **为什么不能整批都赋同一个 `first_seen`**：`first_seen` 是**按抓取批次**打的时间戳 ——
  实测全量 8411 条只有 122 个取值，最大一批覆盖 1857 条。整批同值 = 整批塌成一个时刻，
  与前端「钳到 now」是同一后果（只是把扎堆从超能网换到别的源）。
  实测：60min 阈值下 101 条判伪里有 **68 条落在「同批次多条」上，最大单组 27 条**
  （arxiv_ai_4）、次大 24 条（product_hunt_797）。
  故改为 `_plan_falsify_shifts()`：按 `(源, first_seen)` 分批，**保留组内相对先后**，
  整批后移使**最新的一条**恰好锚在 `first_seen`，其余按原间距排开，下限钳在 72h cutoff 上。
  这与 L3 是同一语义（保序回拉），两层不再互相打架。

### L3 前端钳制不再制造并列（兜底层）

钳制保留（防越界），但改为**保序回拉**：最新的一条拉到 `now`，其余按原始间距排在它之前。
既不越界，也不产生人为同刻。这是 `refresh` 通道（tier-1 JS 重解析）的最后一道网。

### 口径统一

合并 / 72h 裁剪 / 审计 / 输出四处**全部**使用经 L1 校正的公开函数
`_effective_pub_dt(item, fixes)`，避免出现 5 种口径。

**历史文件保持纯净**：`rss_history.json` 只存**原始** `pub_date`，校正只作用于输出副本 `entry`。

## 5. 非目标

- 不改 `api/rss.js`（它读同一份快照，L1/L2 已覆盖其数据源；tier-1 仅 arxiv 一条走 L3）。
- 不替换「预约发布」源（播客/Newsletter 的 `pubDate` 本来就是预约时间）。
- 不改 72h 窗口长度。
- 不为已移除来源（96 个）做数据清理。

## 6. 已知限制

- 冷启动：某源首次进入时历史样本不足 → 第一次构建不做 L1；第二次起生效。
  L2 覆盖冷启动（新条目 `first_seen = now`，未来日期当场判伪）。
- 若上游日后修正了时区标注，检测会自动失效（不再满足倒挂率），无需人工摘除。
- **同刻仍可能存在，但都不是本次引入的：**
  1. **无 `pub_date` 的条目**（无相对信息）：整批统一取 `first_seen` → 同批次同刻。
     实测 `plos_one_678` 30 条 1 个时刻、`愆伏_647` 31 条 2 个时刻。
  2. **组内声称时间完全相同的条目**（如 arxiv 的 `00:00:00-04:00` 日期槽位，
     一批 27 条 adv 全为 +6.7h）：无相对信息可保序 → 仍同刻。实测该块落在列表第 5652 位，远离首屏。
  3. 这两类的视觉影响被前端 `tierInterleave()`（同 tier 连续段 ≤4）限制；
     首屏 120 张的最大同源连续段实测 = 4（before 超能网 / after V2EX，均 ≤4）。

### 附带纠正：一次「看起来像时区误标」的伪阳性

`_tz_survey.py` 曾对 `product_hunt_797` 报出「建议 `pub_date_offset_min=-525`」。
核对原始字符串后**否定**了该结论：

- `product_hunt_797` 原始值 = `2026-09-13T16:07:03-07:00`（PT，**解析正确**），
  超前区间 [+2.2h, +8.2h] 来自**源自身排期**（feed 里就在当天更晚才 featured），不是时区问题；
- `arxiv_ai_4` 原始值 = `2026-09-11T00:00:00-04:00`，**60 条墙钟全是 00:00** —— 是**日期槽位**，
  换算成北京 12:00 只是「午夜 ET」，本身就是日期级精度，不是发布时刻。

若按 -525 写入配置，会**静默改写一个本来正确的源的日期**。
这正是「发现器只报告、校正必须显式声明」这条设计的实证价值：
- `product_hunt_797`：need（下界 = 最大超前）= **491.7min**，中位 439.5min，区间 [0.1, 8.2]h。
  物理约束只给出「≥491.7min」，合法候选 525 / 570 … 全部在可行域内，统计无法唯一判定；
- `arxiv_ai_4`：need = **1431.4min（23.9h）> `TZ_MAX_OFFSET_MIN`(840)** → 发现器正确地
  归类为 `kind='other'`（非时区），不给建议值。

两条都只有**读原始字符串**才能定案。

## 8. 复现与验收实测（A/B，真数据 8105/8117 篇）

受控 A/B：**同一份历史 + 同一份抓到手的 payload**，只切两个变量 ——
A 组（剥掉 `pub_date_offset_min` + 旧钳制「折叠成 now」）vs B 组（当前源码）。
渲染产物在 `.deploy-tmp/serve-tzbefore` / `serve-tzafter`，Playwright 打开同一构建产物读取首屏。

### 8.1 现象复现（A 组 = 用户报告的状态）

首屏前 7 位里有 **6 位是超能网**（第 1、2、3、4、6、7 位），与用户描述一致；
其条目最长同源连续段 **12**（全量顺序里），首条落在 index **0**。

### 8.2 修复效果

| 指标 | A 组（修前） | B 组（修后） |
|---|---|---|
| 超能网 首次出现位置 | **0** | **87** |
| 超能网 首屏 120 位内条数 | **6** | **1** |
| 超能网 最长同源连续段 | **12** | **1** |
| 首屏显示「收录 X」的卡片 | 6 / 120 | **0 / 120** |
| 首屏最长同源连续段 | 4（超能网） | 4（V2EX） |
| 首屏前 15 位含超能网 | 是 | **否** |
| `bad_date` 不可信源数 | 7 | 6（超能网移出） |
| 超能网条目数 / 其中晚于 `first_seen` | 43 / 12 | 31 / **0** |
| 超能网最早时间 | `09-11T13:34`（未校正） | `09-11T14:05`（校正后） |
| 全量 `date_fallback` 条数 | 248 | 206 |

超能网条目 43 → 31：校正后 12 条的真实时间落到 72h 窗口之外，被正常裁剪（这是应有的后果，
不是丢数据 —— 历史文件仍保留它们的原始 `pub_date`）。
