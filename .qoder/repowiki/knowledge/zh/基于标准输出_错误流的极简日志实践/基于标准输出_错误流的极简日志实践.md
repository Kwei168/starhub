## 1. 使用的系统/方法

仓库没有引入任何第三方日志框架（无 `logging`、`loguru`、`winston`、`pino` 等），也没有统一的日志初始化模块。所有“日志”行为通过以下两种原生方式实现：
- Python 侧：使用 `print(..., file=sys.stderr)` 将诊断信息输出到标准错误流。
- JavaScript (Vercel Serverless) 侧：**不主动打印任何日志**，而是依赖 Vercel 平台自动捕获的 HTTP 请求/响应与异常堆栈作为运行期日志；代码中多处注释明确说明“细节由 Vercel 日志记录”。

## 2. 关键文件

| 文件 | 作用 |
|---|---|
| `fetch_and_build.py` | 构建脚本，唯一集中使用 `print(..., file=sys.stderr)` 的地方 |
| `api/refresh.js` | Vercel 函数，无显式日志，依赖平台日志 |
| `api/events.js` | Vercel 函数，无显式日志 |
| `api/search.js` | Vercel 函数，无显式日志 |
| `dev_render.py` | 本地开发工具，仅 `SystemExit` + 成功提示，无错误日志 |

## 3. 架构与约定

### Python 端 (`fetch_and_build.py`)
- **统一 sink**：所有非正常流程的诊断信息一律写入 `sys.stderr`，而非 `stdout`。例如：
  - `[AI池 <topic> 失败] <e>`
  - `[Trending <lang> 失败] <e>`
  - `[关注列表失败] <e>`
  - `[事件拉取失败 <user>] <e>`
  - `[警告] AI 池为空，跳过快照更新，保留旧基线`
  - `[翻译失败-保留原文] <fn>`
  - `[README简介] <fn> -> <摘要>`
  - `[涨星榜] Trending 抓取失败，降级为快照差值模式`
- **结构化字段**：每条日志以方括号包裹的“来源标签”开头（如 `[AI池 ...]`、`[Trending ...]`、`[事件拉取失败 ...]`），便于在 CI/Actions 日志中快速 grep 定位。
- **成功路径**：仅最终汇总输出一次 `print("更新完成：共 %d 个项目" % len(out))` 到 stdout。
- **异常处理**：每个外部调用（GitHub API、翻译服务）都包裹 `try/except Exception`，失败时打印一行 stderr 并继续或 break，不会抛出未捕获异常中断整个构建。

### JavaScript 端 (`api/*.js`)
- **零显式日志**：三个 Serverless 函数内部没有任何 `console.log` / `console.error` / `logger.info` 等调用。
- **平台日志策略**：代码注释明确声明“细节由 Vercel 日志记录”，即依赖 Vercel 对 HTTP 请求、响应体、未捕获异常的自动采集。
- **安全约束**：上游 GitHub API 的错误详情被刻意隐藏（返回通用错误消息），避免向调用者泄露敏感信息；真正的错误细节只出现在 Vercel 平台日志中。

## 4. 约定与约束

| 规则 | 证据来源 |
|---|---|
| Python 诊断信息必须输出到 `stderr`，业务结果输出到 `stdout` | `fetch_and_build.py` 中所有错误/警告均使用 `file=sys.stderr`，最终成功消息使用默认 `stdout` |
| 日志条目必须以 `[来源标签]` 形式开头，便于过滤 | 全库所有 `print(..., file=sys.stderr)` 均遵循该格式 |
| 对外部 API 调用失败必须 catch 并降级，不能抛异常中断 | 多处 `try/except Exception` 包裹 GitHub API、翻译服务调用 |
| JS Serverless 函数禁止向响应体回显上游错误细节 | `refresh.js`、`search.js` 注释写明“不向上游调用者回显 GitHub 错误细节（防信息泄露），细节由 Vercel 日志记录” |
| 日志不包含结构化 JSON 字段，仅为人类可读文本 | 全库无任何 `json.dumps` 包装的日志输出，也无日志级别枚举 |

## 5. 总结

这是一个**极简日志体系**：Python 构建脚本用 `stderr` + 方括号标签的纯文本日志，JS Serverless 完全依赖云平台日志采集。没有日志级别、没有结构化字段、没有集中配置，但通过一致的标签前缀和明确的 stderr/stdout 分工，足以满足 GitHub Actions 构建日志排查与 Vercel 运行时问题定位的需求。
